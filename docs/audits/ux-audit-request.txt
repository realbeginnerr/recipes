# 웹사이트 UX 및 예외 대응 진단 (UX Audit)

## 0. 분석 목적

이번 작업의 목적은 발생 가능한 시나리오를 많이 발굴하는 것이 아니다.

**현재 웹사이트가 다양한 사용자 상황에 적절하게 대응하도록 설계·구현되어 있는지 확인하고, UX 사용성이 좋지 않은 부분을 발견하여 개선하는 것이 핵심 목적이다.**

다음 두 가지를 중점적으로 검토한다.

### A. 예외 상황 대응 준비 상태

오류, 엣지 케이스, 시스템 상태 변화 등이 발생했을 때 다음 사항이 준비되어 있는지 확인한다.

- 사용자에게 적절한 화면이나 메시지가 표시되는가?
- 사용자가 현재 상황과 문제 원인을 이해할 수 있는가?
- 문제를 해결하거나 이전 작업으로 복귀할 방법이 있는가?
- 입력 중이던 데이터나 작업 결과가 안전하게 보존되는가?
- 로딩, 빈 데이터, 성공, 실패, 권한 부족 등의 상태에 적절하게 대응하는가?
- UI뿐 아니라 필요한 실제 처리 로직도 구현되어 있는가?

### B. UX 사용성 진단

정상적인 사용 흐름에서도 다음과 같은 UX 문제를 발견한다.

- 사용자가 다음에 무엇을 해야 할지 알기 어려운 부분
- 메뉴 구조나 화면 이동이 직관적이지 않은 부분
- 불필요하게 많은 클릭이나 입력이 필요한 부분
- 버튼, 라벨, 안내 문구의 의미가 불명확한 부분
- 사용자가 실수하기 쉬운 인터페이스
- 작업 완료 여부를 알기 어려운 부분
- 일관성이 부족한 UI와 상호작용
- 사용자의 기대와 실제 동작이 다른 부분
- 접근성 및 반응형 사용성 문제

Jakob Nielsen의 10가지 사용성 휴리스틱을 UX 진단 기준으로 활용한다.

## 1. 분석 범위

전체 프로젝트를 한 번에 상세 분석하지 않는다.

이번 UX Audit의 분석 대상은 내비게이션의 '레시피' 메뉴로 한정한다.

- '레시피' 메뉴에 속한 모든 하위 페이지, 기능, 사용자 흐름을 분석한다.
- 레시피 목록, 상세, 등록, 수정, 삭제 등 실제로 존재하는 기능을 대상으로 한다.
- 다른 내비게이션 메뉴는 분석 대상에서 제외한다.
- 단, '레시피' 메뉴의 기능과 직접 연결된 공통 기능(로그인, 권한, 데이터 저장 등)은 필요한 범위에서 함께 검토한다.
- 분석 결과는 '레시피' 메뉴에 대한 UX 문제점, 예외 상황 대응 누락, 구체적인 개선안을 중심으로 작성한다.

먼저 해당 메뉴의 하위 화면과 주요 기능을 파악한 다음, 각 화면의 현재 구현 상태를 분석한다.

다음 자료를 참고한다.

- PRD.md
- IA.yaml
- project-checklist.md
- design-system.md
- 실제 프런트엔드 코드
- 관련 백엔드 및 API 코드(접근 가능한 경우)
- 실제 실행 화면(확인 가능한 경우)

문서에 정의된 내용과 실제 구현 상태를 구분한다.

코드만으로 사용성을 확정할 수 없는 항목은 실제 화면 검증이 필요하다고 표시한다.

## 2. 진단 기준

다음 5가지 범주를 점검 기준으로 활용한다.

1. Normal & Alternative Flows
2. Error & Exception Cases
3. Edge & Boundary Cases
4. UI & System States
5. Security & Abuse Cases

각 범주에 속하는 시나리오를 무조건 많이 만들 필요는 없다.

실제 사용자 경험에 영향을 주는 중요한 상황을 우선 검토한다.

각 상황에 대해 다음 질문에 답한다.

1. 해당 상황에 대한 대응이 필요한가?
2. PRD 또는 디자인 시스템에 대응 정책이 정의되어 있는가?
3. 실제 코드에 대응 로직이 구현되어 있는가?
4. 사용자에게 적절한 UI와 메시지가 제공되는가?
5. 현재 대응 방식에 UX 문제가 있는가?
6. 개선이 필요하다면 무엇을 어떻게 변경해야 하는가?

## 3. 대응 상태 판정

각 점검 항목에 다음 상태를 부여한다.

- 적절함: 필요한 대응이 정의·구현되어 있고 확인 가능한 범위에서 UX 문제가 없음
- 개선 필요: 대응은 존재하지만 UX 또는 처리 방식에 문제가 있음
- 누락: 필요한 대응이 정의되거나 구현되지 않음
- 확인 필요: 자료가 부족하여 판단할 수 없음
- 해당 없음: 현재 기능과 관련 없는 상황

PRD에 정의되어 있지만 구현되지 않은 경우와, 구현되어 있지만 PRD에 정의되지 않은 경우를 구분하여 기록한다.

실제 확인하지 않은 동작을 정상이라고 추정하지 않는다.

## 4. UX 문제 발견 및 개선안

문제를 발견하면 단순히 문제만 나열하지 말고 다음 내용을 포함한다.

- 현재 상태: 지금 어떤 화면과 동작이 존재하는가?
- 문제점: 무엇이 부족하거나 잘못되었는가?
- 사용자 영향: 사용자에게 어떤 불편이나 위험이 발생하는가?
- 개선안: 화면, 메시지, 인터랙션 또는 처리 로직을 어떻게 변경해야 하는가?
- 권장 UI: 기존 디자인 시스템과 Carbon 컴포넌트를 우선 활용한다.
- 권장 문구: 필요한 경우 실제 화면에 사용할 메시지를 작성한다.
- 복구 방법: 재시도, 이전 화면 복귀, 입력값 보존 등 필요한 후속 동작을 정의한다.

가능하면 코드 파일과 관련 위치를 근거로 제시한다.

## 5. 우선순위

발견된 문제의 심각도에 따라 우선순위를 부여한다.

- P0: 보안 문제, 데이터 손실, 핵심 기능 중단 등 치명적인 문제
- P1: 주요 작업 수행에 지장을 주거나 심각한 사용성 문제를 유발하는 경우
- P2: 상대적으로 영향이 작지만 개선할 가치가 있는 문제

문제가 아닌 정상 구현 항목에는 개선 우선순위를 부여하지 않는다.

## 6. 출력 형식

### A. 분석 범위 요약

분석한 메뉴, 하위 화면, 주요 기능을 먼저 제시한다.

### B. 진단 요약

- 점검 항목 수
- 적절함
- 개선 필요
- 누락
- 확인 필요
- 해당 없음

### C. 문제 및 개선안

다음 표를 작성한다.

| ID | 화면/기능 | 진단 범주 | 현재 상태 | 발견된 문제 | 사용자 영향 | 판정 | 우선순위 | 구체적인 개선안 |
|---|---|---|---|---|---|---|---|---|

'개선 필요' 또는 '누락'으로 판정한 항목을 중심으로 작성한다.

각 항목에는 현재 구현 상태를 확인한 근거를 함께 제공한다.

필요한 경우 개선할 화면 구조, UI 컴포넌트, 안내 문구, 후속 동작을 표 아래에 구체적으로 제안한다.

### D. 정상 대응 항목

이미 적절하게 구현된 항목은 간단히 요약한다.

정상 대응 항목을 문제 목록에 반복해서 작성하지 않는다.

### E. 확인이 필요한 항목

실제 화면 테스트나 추가 정책 결정이 필요한 사항을 별도로 정리한다.

## 7. 작업 순서

1. 지정한 메뉴와 관련된 문서 및 코드를 분석한다.
2. 해당 메뉴의 화면과 기능 목록을 작성한다.
3. 중요한 사용자 흐름과 예외 상황을 점검한다.
4. 현재 대응 정책과 실제 구현 상태를 확인한다.
5. UX 문제와 대응 누락을 발견한다.
6. 문제의 심각도에 따라 우선순위를 부여한다.
7. 구체적인 UI·메시지·동작 개선안을 제안한다.
8. 내가 검토하고 승인할 때까지 기다린다.

**내 승인 전에는 PRD, 디자인 시스템, 소스코드 등 어떤 파일도 수정하지 않는다.**

이번 작업의 최종 결과물은 시나리오 목록이 아니라 **현재 웹사이트의 UX 문제점과 예외 대응 누락 사항을 확인하고 개선할 수 있는 진단 보고서**여야 한다.
