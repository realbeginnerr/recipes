이 문서는 **만들기 전에 결정할 사항**과 **어느 정도 만든 뒤 실제 동작을 검토할 방법**을 함께 관리한다. 제작 전 답을 정했다는 것과 구현·검증이 끝났다는 것은 다르다.

| 단계 | 사용할 부분 | 남길 결과 |
| --- | --- | --- |
| 제작 전·기획 | 1부의 목적·사용자·지원 환경·기능·운영 검토, 2부의 필요한 상세 항목 | 요구사항·지원 범위·상태별 처리·완료 조건을 요구사항 문서에 기록 |
| UI 설계·구현 중 | 2부의 인터랙션·상태·예외·콘텐츠·문구 체크리스트 | 설계안·실제 코드에 반영하고 미구현·미결 사항을 구분 |
| 프로토타입·제작 중·출시 전후 | 3부의 범위 설정·사용성 질문·판정·개선안·우선순위 | 코드와 화면 근거를 붙인 Audit 결과 및 검증 한계 |

새 사이트는 1부부터 시작하고, 기존 사이트의 일부 화면은 3부에서 범위를 정한 뒤 해당하는 1·2부 항목을 참조한다. 같은 질문을 단계마다 복제하지 않고, **제작 전에는 정책을 결정하고 제작 중·후에는 그 정책이 실제로 구현되어 사용하기 좋은지 확인**한다. 상세 UX 라이팅 규칙은 관리 필요성이 생기면 별도 문서로 분리하되 같은 규칙을 중복 정의하지 않는다.

## 사용·기록 원칙

| 문서·산출물 | 역할 |
| --- | --- |
| 본 통합 가이드 | 공통 검토 기준, 오류·엣지 케이스의 범주와 필수 질문을 제공한다. |
| PRD | 프로젝트별 발생 조건, 허용·차단 기준, 사용자 대응·복구 흐름과 완료 조건을 정의한다. |
| 디자인 시스템 | 여러 화면에서 재사용하는 UI 요소별 오류 표현·문구 원칙·스타일·인터랙션 규칙을 정의한다. 이 프로젝트의 파일은 `docs/design-system.md`다. |
| QA 테스트·검증 기록 | PRD의 처리 조건과 디자인 시스템의 동작·표현이 구현되었는지 확인한다. 자동 테스트와 수동 검증의 범위·결과를 구분한다. |

상세 질문은 공통 체크리스트에서 관리하고 Audit 결과는 해당 질문과 근거를 연결한다. 특정 기능에만 적용하는 예외는 PRD에 두며, 다른 기능에서도 재사용할 규칙이 되면 디자인 시스템으로 옮긴다.

하나의 정책은 한 문서에서 정의하고 다른 문서에서는 해당 항목을 참조한다. PRD에는 적용할 공통 UI 패턴을 명시하고, QA에서는 관련 요구사항·패턴과 검증 결과를 연결한다. 체크리스트에 항목이 있다는 사실을 설계·구현·검증 완료로 해석하지 않는다. PRD 등 필요한 문서가 없다면 해당 결정의 기록 위치를 마련하고, 임시 기록은 임시 상태임을 명시한다.

예: 환산값이 없는 단위를 선택하는 경우, 체크리스트는 계산 데이터 누락 여부를 묻는다. PRD는 선택·저장 차단과 환산값 등록 안내라는 대응을 정의한다. 디자인 시스템은 필드 아래 오류 문구·오류 테두리·접근성 전달 방식을 정의한다. QA는 경고 표시, 선택·저장 차단, 기존 입력값 유지 여부를 확인한다.

체크박스는 해당 항목의 검토가 완료되었음을 의미한다. 결정 결과는 항목의 성격에 맞게 기록한다. 예를 들어 사용자 유형·기능은 ‘지원 / 미지원 / 추후 지원’, 표기 규칙은 ‘사용 / 사용 안 함’, 수치 기준은 구체적인 값과 단위로 적는다. 적용하지 않는 항목도 그 이유를 기록한 뒤 검토 완료로 표시한다. 체크박스가 없는 세부 목록에도 같은 기록 원칙을 적용한다.

### 02. 사용자 정의

어떤 사용자까지 고려해 제품을 만들 것인지 아래 목록을 검토하고, 지원 범위와 사용자별 요구사항을 구체적으로 정한다.

**이용 관계와 계정 유형**

- [ ] 비회원
- [ ] 회원
- [ ] 개인 고객
- [ ] 기업·단체 고객
- [ ] 개인 계정과 조직 계정 — 제공 여부와 계정별 이용 방식

**연령과 신체·접근성 조건**

- [ ] 어린이 및 미성년자 — 지원 연령대와 보호자 관여가 필요한 범위
- [ ] 70세 이상 고령층
- [ ] 시각 장애인 (저시력, 색맹 포함)
- [ ] 청각 장애인
- [ ] 상체 장애인 (특히 팔, 손)
- [ ] 하체 장애인
- [ ] 장애인은 아니지만 일시적으로 시각·청각·상체·하체 등 신체 특정 부위를 사용하기 어려운 사람 (예: 교통사고로 당분간 목발을 사용해야 하는 사람)

**거주 지역·언어·접속 환경**

- [ ] 주 서비스 지역 외의 장소에 거주하는 사람 (예: 해외 거주 한국인)
- [ ] 인터넷 연결이 불안정하거나 불가능한 지역에 있는 사람 (예: 섬, 지방 소도시 중 인터넷 미지원 지역, 재난 지역)
- [ ] 외국인 — 국적만으로 구분하지 않고 사용 언어, 거주 국가, 서비스 이용 조건에 따른 요구사항 정의

**이용 비용과 결제 수단**

- [ ] 저소득층·소득이 없거나 지불 여력이 제한된 사람 — 대상 기준과 이용 비용의 부담 수준 정의 (예: 수입 없는 학생)
- [ ] 결제 수단 접근이 제한된 사람 (예: 신용 문제로 특정 결제 수단을 사용할 수 없는 사람)

**운영 역할과 서비스 지원 범위**

- [ ] 관리자 페이지가 필요한가?
- [ ] 관리자, 운영자, 일반 사용자 등 역할과 관리자 종류를 어떻게 나누고, 역할별 담당 업무를 어떻게 정할 것인가? 세부 접근 권한은 15장 7절에서 검토한다.
- [ ] 다국어 또는 국가별 서비스를 제공해야 하는가?

### 04. 사용 기기 및 환경

- [ ] 제공 형태는 웹 / 앱 중 무엇인가? 둘 다 제공한다면 기능과 데이터는 어떻게 연결할 것인가?
- [ ] 웹의 레이아웃 대응은 반응형 / 적응형 중 무엇인가? 혼합한다면 적용 범위는 무엇인가?
- [ ] 모바일용·PC용 사이트를 별도로 운영할 필요가 있는가?
- [ ] 앱이라면 어떤 기기에 맞춰 작동하도록 만들 것인가? 화면 너비·높이의 최소 지원 범위와 크기별 레이아웃 대응을 어떻게 정할 것인가?
- [ ] 반응형 웹이라면 여러 기기에서 화면이 어떻게 유동적으로 변할 것인가? 브레이크포인트(BP)는 어떤 기준과 값으로 설정할 것인가?

제품을 만들 때 아래 기기 중 어디까지 고려할지 정한다. 각 항목에 지원 기종·환경, 레이아웃 설계의 기준 기기, 실제 검증할 테스트 대상 기기를 구분해 적는다. 화면 크기는 물리적 크기·해상도와 UI에서 사용하는 논리적 너비·높이(웹의 CSS px 등)를 구분해 기록한다.

- [ ] 모바일 — 지원할 아이폰 기종은 무엇이며, 대표 기준 기종은 무엇인가?
- [ ] 모바일 — 지원할 갤럭시 기종은 무엇이며, 대표 기준 기종은 무엇인가?
- [ ] 모바일 — 그 외 지원할 제조사·기종과 대표 기준 기종은 무엇인가?
- [ ] PC (노트북 포함) — 지원할 화면 크기·해상도와 대표 기준 환경은 무엇인가?
- [ ] 태블릿 — 어떤 종류와 기종을 지원하며, 대표 기준 기종은 무엇인가?
- [ ] 스마트 워치 — 지원할 종류·기종과 대표 기준 기종은 무엇인가?
- [ ] TV — 지원할 종류·기종과 대표 기준 환경은 무엇인가?
- [ ] VR — 지원할 기기와 대표 기준 기종은 무엇인가?

- [ ] 지원할 브라우저와 최소 버전은 무엇인가?
- [ ] 지원할 운영체제는 무엇인가?
- [ ] 화면 방향(가로 / 세로)에 따른 별도 대응이 필요한가?
- [ ] 느린 네트워크나 저사양 기기까지 지원해야 하는가?

## 2부. 설계·구현 공통 — 인터랙션·상태·예외·콘텐츠 점검

제작 전에는 필요한 행동과 상태별 정책을 정하는 질문으로, 제작 중·후에는 설계·구현 누락을 찾는 질문으로 사용한다. 아래 상세 질문은 한 번만 관리하고 Audit 결과에서 관련 항목을 참조한다.

<a id="section-15"></a>

### 15. 사용자 인터랙션 및 UI 상태 (Interaction & UI States)

사용자의 행동에 따라 컴포넌트와 화면이 어떻게 변화해야 하는지 검토한다. 프로젝트에서 필요한 시나리오를 선정하고, 각 시나리오에 따른 UI 상태와 화면을 설계한다.

각 사용자 행동에 대해 필요한 공통 UI 상태를 함께 검토한다. 공통 상태의 표현과 처리 원칙은 이 챕터의 ‘공통 UI 상태’에서 정의하고, 행동별로 다른 안내 문구·후속 작업·예외 처리는 해당 행동 항목에 기록한다.

이하 절 번호는 모두 15장 내부 번호다. 8절은 공통 상태의 목록, 9절은 입력 방식, 10절은 오류·복구 시나리오, 11절은 콘텐츠 표시, 12절은 메시지 표현을 다룬다. 같은 결정을 반복해서 기록하지 않고 해당 절을 참조한다. 9·11절은 Atomic Design의 모든 단계(Atoms, Molecules, Organisms, Templates, Pages)에 적용한다.

<a id="checks-1"></a>

#### 1. 선택 (Selection)

- 단일 항목 선택
- 다중 항목 선택
- 단일 항목 선택 해제
- 다중 항목 선택 해제
- 전체 선택
- 전체 선택 해제
- 전체 선택·해제의 대상 범위 정의 (현재 페이지 / 검색·필터 결과 전체 / 전체 데이터)
- 선택 가능한 항목과 선택 불가능한 항목 구분
- 선택된 항목 수 표시
- 선택된 항목에 대한 일괄 작업 제공

<a id="checks-2"></a>

#### 2. 생성 (Create)

- 단일 항목 생성
- 다중 항목 일괄 생성
- 필수 입력 항목 정의
- 선택 입력 항목 정의
- 입력값 유효성 검사
- 임시 저장
- 생성 취소

<a id="checks-3"></a>

#### 3. 수정 (Update)

- 단일 항목 수정
- 다중 항목 일괄 수정
- 변경 사항 저장
- 변경 사항 취소
- 저장하지 않은 변경 사항에 대한 경고

<a id="checks-4"></a>

#### 4. 삭제 (Delete)

- 단일 항목 삭제
- 다중 항목 일괄 삭제
- 전체 삭제
- 전체 삭제의 대상 범위 정의 (현재 페이지 / 검색·필터 결과 전체 / 전체 데이터)
- 삭제 전 확인
- 삭제 취소 또는 복구
- 삭제 방식과 복구 조건 정의 (영구 삭제 여부, 복구 가능 기간, 복구 권한)

<a id="checks-5"></a>

#### 5. 정보 조회 (Read & View)

사용자가 필요한 정보나 콘텐츠를 어떤 방식으로 조회할 수 있어야 하는지 검토한다.

- 단일 항목 조회
- 다중 항목 목록 조회
- 항목의 상세 정보 조회
- 여러 항목의 정보 비교
- 목록과 상세 화면 간 이동
- 정보 검색
- 필터링 및 정렬
- 페이지네이션 또는 무한 스크롤
- 정보가 사용자의 이해·작업 순서대로 배치되며, 이전 화면의 내용을 외우지 않고 선택지·현재 필터를 확인할 수 있는가?
- 초보자의 핵심 작업과 숙련자의 반복 작업을 함께 검토하고, 다중 선택·일괄 작업·개인 설정 등 효율화 수단이 필요한가?

콘텐츠 누락·일부 제공 등 표시 예외는 11절에서 검토한다.

<a id="checks-6"></a>

#### 6. 도움말 및 문제 해결 (Help & Support)

사용자가 특정 기능이나 정보를 이해하지 못하거나 문제가 발생했을 때 도움을 받을 수 있는 방법을 검토한다.

- 특정 요소에 대한 설명 제공 (Tooltip, Help Text)
- 기능 사용 방법 안내
- 복잡한 작업에 실제로 따라 할 수 있는 단계별 절차 제공
- 처음 사용하는 사용자를 위한 온보딩
- 입력 항목에 대한 작성 예시 제공
- 이해하기 어려운 용어에 대한 설명 제공
- 자주 묻는 질문 (FAQ)
- 고객 지원 또는 관리자에게 문의
- 문제 신고 및 피드백 제출
- 사용자가 도움말을 쉽게 찾을 수 있는 진입점 제공

<a id="checks-7"></a>

#### 7. 공개 범위 및 접근 권한 (Visibility & Permissions)

정보의 공개 범위와 사용자별 접근 권한을 정의하고, 권한에 따라 UI가 어떻게 달라져야 하는지 검토한다.

**공개 범위**

- 전체 공개
- 회원에게만 공개
- 특정 사용자 또는 그룹에게만 공개
- 비공개
- 공개 범위 변경
- 공개 예정 또는 예약 공개
- 공개 기간 설정
- 공개 범위에 따른 정보 노출 차이

**접근 권한**

- 사용자 역할별 권한 정의 (관리자, 일반 회원 등)
- 정보 조회 권한
- 정보 생성 권한
- 정보 수정 권한
- 정보 삭제 권한
- 다운로드 및 공유 권한
- 다른 사용자에게 권한 부여
- 부여한 권한 변경 및 회수

권한 오류 및 작업 도중 권한 변경은 10.4절, 접근 제한 콘텐츠의 표시는 11.5절에서 검토한다.

<a id="checks-8"></a>

#### 8. 공통 UI 상태 (UI States & Exceptions)

조회·선택·생성·수정·삭제 등 각 행동에 필요한 상태를 선정하고, 아래 공통 원칙을 적용한다. 상태별로 사용자에게 표시할 내용, 가능한 작업, 다음 화면으로의 전환을 정한다.

- 기본 상태 (Default)
- 호버 상태 (Hover)
- 포커스 상태 (Focus)
- 선택 상태 (Selected) — 11.1절 참조
- 비활성 상태 (Disabled) — 사용할 수 없는 이유와 활성화 조건은 11.4절 참조
- 로딩 상태 (Loading) — 12.3절 참조
- 빈 데이터 상태 (Empty) — 11.2절 참조
- 오류 상태 (Error) — 10절 참조
- 성공 상태 (Success) — 작업 완료 안내와 후속 작업 또는 이동 경로 제공
- 권한 부족 상태 (Permission Denied) — 발생 조건은 10.4절, 표시 방식은 11.5절 참조

<a id="checks-9"></a>

#### 9. 입력 방식별 인터랙션 (Input Methods & Interactions)

사용자가 마우스, 키보드, 터치, 음성 등 다양한 입력 방식으로 인터페이스를 조작할 때 발생할 수 있는 상황을 검토한다.

각 항목에 대해 다음 사항을 검토한다.

- 해당 입력 방식을 지원해야 하는가?
- 사용자의 행동에 따라 어떤 기능이 실행되는가?
- 컴포넌트의 시각적 상태가 어떻게 변화하는가?
- 피드백(모션, 메시지, 소리 등)이 필요한가?
- 해당 입력 방식을 사용할 수 없는 경우 대체 조작 방법이 있는가?

##### 9.1 마우스 인터랙션 (Mouse Interactions)

**클릭**

- 왼쪽 버튼 단일 클릭 (Single Click)
- 왼쪽 버튼 더블 클릭 (Double Click)
- 오른쪽 버튼 클릭 및 컨텍스트 메뉴 (Right Click)
- 클릭 후 눌린 상태 (Pressed / Active)
- 요소 외부 클릭 (Click Outside) — 팝업, 모달, 드롭다운 등의 닫힘·유지 동작
- 클릭할 수 없는 요소를 클릭했을 때 (Disabled / Non-interactive)

**포인터 및 이동**

- 마우스 올리기 (Hover)
- 마우스 포인터가 요소를 벗어났을 때 (Mouse Leave)
- 마우스 드래그 (Drag)
- 드래그 앤 드롭 (Drag & Drop)
- 드래그 중 이동 가능한 영역과 불가능한 영역 표시
- 드래그 취소 및 원래 위치로 복귀
- 슬라이더 조작 (Slider Interaction)

**스크롤**

- 세로 스크롤
- 가로 스크롤
- 스크롤 시작 및 종료
- 스크롤 위치에 따른 UI 변화 (Sticky Header 등)
- 스크롤 가능한 영역과 불가능한 영역 구분

##### 9.2 키보드 인터랙션 (Keyboard Interactions)

**기본 조작**

- Enter 키 (실행, 검색, 제출 등)
- Tab 키 (다음 요소로 포커스 이동)
- Shift + Tab (이전 요소로 포커스 이동)
- Escape 키 (닫기, 취소, 선택 해제 등)
- Space 키 (버튼 실행, 체크박스 선택 등)
- 방향키 (목록, 메뉴, 옵션 이동)
- Home / End 키
- Page Up / Page Down 키

**텍스트 입력**

- 영문 및 한글 입력
- 한글 IME 조합 중 입력 처리
- 숫자 입력
- 특수문자 입력
- 복사 및 붙여넣기
- 잘라내기
- 실행 취소 및 다시 실행 (Undo / Redo)

입력값 제한과 검증 오류는 10.1절에서 검토한다.

**접근성 및 포커스**

키보드 지원 범위는 03장에서 정하고, 여기서는 구체적인 조작을 검토한다.
- 포커스 이동 순서가 논리적인가?
- 현재 포커스 위치가 시각적으로 표시되는가?
- 모달이 열렸을 때 포커스 이동 및 복귀
- 키보드 단축키 제공 여부
- 단축키 충돌 및 오작동 방지

##### 9.3 터치 인터랙션 (Touch Interactions)

**탭**

- 단일 탭 (Single Tap)
- 더블 탭 (Double Tap)
- 길게 누르기 (Long Press)
- 탭 가능한 영역과 불가능한 영역 구분
- 터치 영역 크기 및 간격 적절성

**이동 및 제스처**

- 팬 (Pan) — 확대된 콘텐츠나 화면 이동
- 드래그 (Drag) — 요소 위치 이동
- 드래그 앤 드롭 (Drag & Drop)
- 스와이프 (Swipe) — 화면 전환, 닫기 등
- 플릭 (Flick) — 빠른 스와이프 및 관성 이동
- 핀치 아웃 (Pinch Out) — 확대
- 핀치 인 (Pinch In) — 축소
- 회전 (Rotate)
- 두 손가락 탭
- 두 손가락 더블 탭
- 두 손가락 스와이프
- 제스처 도중 취소 또는 중단

**터치 환경 특수 상황**

- 운영체제 기본 제스처와 충돌 여부
- 의도하지 않은 터치 및 중복 탭 방지
- 터치 피드백 (시각, 진동 등)
- 마우스 Hover에만 의존하는 기능의 대체 UI
- 터치와 스크롤 동작 간 충돌 여부

##### 9.4 음성 인터랙션 (Voice Interactions)

음성 입력 및 음성 명령을 지원하는 프로젝트에 적용한다.

- 음성 입력 시작
- 음성 입력 중 상태 표시
- 음성 입력 일시정지 및 종료
- 음성 인식 결과 표시
- 잘못 인식된 내용 수정
- 음성 명령 실행 전 확인
- 음성 인식 실패 및 재시도
- 마이크 접근 권한 요청 및 거부
- 주변 소음 및 음성 인식 불가 상황
- 음성 기능을 사용할 수 없는 경우 대체 입력 제공

<a id="checks-10"></a>

#### 10. 오류 및 예외 상황 (Errors & Edge Cases)

사용자의 행동, 시스템 상태, 네트워크 환경, 데이터 상태 등에 따라 발생할 수 있는 오류와 예외 상황을 검토한다.

각 오류에 대해 다음 사항을 정의한다.

프로젝트별 결정과 공통 UI 규칙의 기록 위치는 [사용·기록 원칙](#recording)을 따른다.

- 오류 발생 조건
- 사용자에게 표시할 메시지
- 오류를 표시할 UI 형태 (Inline, Toast, Modal 등)
- 사용자가 취할 수 있는 해결 행동과 재시도·복구 방법
- 입력 중이던 데이터 및 작업 상태 보존 여부

<a id="checks-10-1"></a>

##### 10.1 사용자 입력 오류 (Input Errors)

- 필수 항목 누락
- 허용되지 않는 문자 입력
- 입력값 길이 초과 또는 미달
- 잘못된 데이터 형식
- 중복된 데이터 입력
- 유효하지 않은 값 입력
- 입력값 간 조건 불일치
- 입력 전에 필드 목적·형식·제약·예시를 안내하고, 잘못된 입력을 예방하거나 수정할 수 있는가?

##### 10.2 네트워크 및 시스템 오류 (Network & System Errors)

- 인터넷 연결 끊김
- 네트워크 응답 지연
- 서버 오류
- 요청 시간 초과 (Timeout)
- 데이터 불러오기 실패
- 데이터 저장 실패
- 파일 업로드 및 다운로드 실패

일부 요청만 성공한 경우의 처리는 10.5절에서 검토한다.

##### 10.3 데이터 및 콘텐츠 예외 (Data & Content Edge Cases)

- 삭제되었거나 존재하지 않는 콘텐츠
- 다른 사용자에 의해 데이터가 변경된 경우
- 데이터 충돌 및 중복 처리

빈 데이터·검색 결과는 11.2절, 콘텐츠 양과 길이는 11.6절, 미디어 로딩 실패는 11.7절에서 검토한다.

##### 10.4 인증 및 권한 오류 (Authentication & Permission Errors)

- 로그인하지 않은 상태
- 로그인 세션 만료
- 접근 권한 부족
- 수정 또는 삭제 권한 없음
- 인증 실패
- 외부 서비스 연결 해제
- 권한이 작업 도중 변경된 경우

<a id="checks-10-5"></a>

##### 10.5 작업 중단 및 복구 (Interruption & Recovery)

- 작업 도중 페이지를 이탈한 경우
- 생성·수정 중 임시 저장과 미저장 변경 경고(2·3절)를 페이지 이탈·브라우저 종료 시 어떻게 적용할지 검토
- 작업 도중 브라우저가 종료된 경우
- 중복 클릭 또는 중복 제출
- 작업 취소
- 작업 실패 후 재시도
- 이전 상태로 복구 및 복구한 작업의 재실행 (Undo / Restore / Redo)
- 여러 항목 또는 요청 중 일부만 성공한 경우 (Partial Success)

##### 10.6 오류 메시지 및 피드백 (Error Messages & Feedback)

- 오류가 발생한 위치 명확히 표시
- 오류 메시지의 시각적 일관성 유지
- 색상 외에도 텍스트·아이콘으로 오류 전달
- 오류 해결 후 성공 피드백 제공

오류별 원인·해결 행동은 10절 도입부에 기록한다. 문체는 12.4절, 메시지 표시 및 스크린 리더 전달 방식은 12.6절, 이해도 검증은 12.7절에서 검토한다.

<a id="checks-11"></a>

#### 11. 정보 표시 및 콘텐츠 상태 (Content Presentation & States)

사용자에게 제공하는 정보의 상태, 양, 형식에 따라 컴포넌트와 화면이 어떻게 표시되어야 하는지 검토한다.

각 항목에 대해 다음 사항을 검토한다.

- 해당 상황이 프로젝트에서 발생할 수 있는가?
- 어떤 UI로 정보를 표시할 것인가?
- 상태에 따른 시각적 차이가 명확한가?
- 모션이나 추가 피드백이 필요한가?
- 접근성과 반응형 환경을 고려했는가?

##### 11.1 선택 상태 (Selection States)

- 선택되지 않은 상태 (Unselected)
- 단일 항목이 선택된 상태 (Single Selected)
- 여러 항목이 선택된 상태 (Multiple Selected)
- 전체 항목이 선택된 상태 (All Selected)
- 일부 항목만 선택된 상태 (Indeterminate)
- 선택 상태를 색상 외에도 아이콘, 체크 표시 등으로 구분
- 선택 상태가 변경될 때 시각적 피드백 제공

##### 11.2 데이터가 없는 상태 (Empty States)

- 텍스트 데이터가 없는 경우
- 이미지 데이터가 없는 경우
- 목록에 표시할 항목이 없는 경우
- 검색 및 필터 결과가 없는 경우
- 아직 콘텐츠가 생성되지 않은 경우
- 텍스트 플레이스홀더 사용 여부
- 이미지 플레이스홀더 또는 대체 이미지 사용 여부
- 빈 상태에 대한 설명 제공
- 필요한 경우 콘텐츠 생성 등 다음 행동 안내

##### 11.3 확인 및 미확인 상태 (Read & Unread States)

- 확인한 콘텐츠와 확인하지 않은 콘텐츠 구분
- 텍스트 굵기, 아이콘, 배지 등 표시 방법 정의
- 읽음 처리 조건 정의 (목록 노출 / 상세 열람 / 직접 확인 버튼 등)
- 미확인 항목 수 표시
- 모든 항목을 확인한 경우 표시
- 확인 및 미확인 상태를 사용자가 직접 변경할 수 있는지 결정

##### 11.4 비활성화 상태 (Disabled States)

조작할 수 없는 상태, 읽기 전용 상태, 접근 제한 상태, 단순히 시각적으로 강조를 낮춘 상태를 구분한다. 텍스트·이미지는 어떤 조작이 제한되는지 명시하고, 접근 제한에 따른 노출 처리는 11.5절에서 정한다.

- 텍스트 콘텐츠의 비활성화 표시
- 이미지 콘텐츠의 비활성화 표시
- 버튼의 비활성화 표시
- 체크박스 및 라디오 버튼의 비활성화 표시
- 스위치의 비활성화 표시
- 입력 필드의 비활성화 표시
- 비활성화된 이유와 활성화 조건 안내
- 비활성화 상태와 읽기 전용 상태 구분
- 비활성화 상태에서도 필요한 정보의 가독성 확보

##### 11.5 비공개 및 접근 제한 상태 (Private & Restricted States)

- 비공개 텍스트 표시 방법
- 비공개 이미지 표시 방법
- 비공개 동영상 및 미디어 표시 방법
- 개인정보 일부 마스킹 처리
- 콘텐츠 전체 숨김 또는 대체 UI 제공
- 비공개 콘텐츠임을 나타내는 아이콘·문구 제공
- 접근 권한이 없는 경우 안내
- 권한 요청 또는 로그인 유도
- 비공개 콘텐츠가 화면·알림·미리보기 등을 통해 노출되지 않도록 검토

<a id="checks-11-6"></a>

##### 11.6 콘텐츠 양과 크기에 따른 표시 (Content Size & Volume)

아래의 ‘짧은·긴·많은·큰’ 조건은 프로젝트별 글자 수, 항목 수, 이미지 크기, 파일 용량 등으로 구체화한다. 최소·일반·최대 테스트 데이터와 허용 성능 기준을 정하고, 상한이 없는 데이터는 테스트 규모와 추가 증가 시 처리 방식을 기록한다.

**콘텐츠가 적을 때**

- 텍스트가 매우 짧은 경우
- 목록에 항목이 1개만 있는 경우
- 이미지가 1개만 있는 경우
- 콘텐츠가 적어 화면에 빈 공간이 많이 생기는 경우
- 최소 데이터로 화면 테스트

**콘텐츠가 많을 때**

- 텍스트가 매우 긴 경우
- 긴 단어·URL 등 줄바꿈이 어려운 경우
- 목록에 항목이 매우 많은 경우
- 이미지 크기 또는 파일 용량이 매우 큰 경우
- 테이블에 행이나 열이 매우 많은 경우
- 텍스트 줄바꿈 및 말줄임 처리
- 콘텐츠 영역 확장 및 축소
- 더 보기 / 접기 기능
- 스크롤, 페이지네이션, 가상 스크롤 적용 여부
- 최대 데이터로 화면 및 성능 테스트

##### 11.7 콘텐츠 품질 및 형식의 예외

- 이미지 비율이 예상과 다른 경우
- 이미지 해상도가 낮은 경우
- 이미지 또는 미디어 로딩에 실패한 경우
- 지원하지 않는 파일 형식인 경우
- 다양한 언어 및 문자 길이
- 숫자가 매우 크거나 작은 경우
- 오래되었거나 갱신되지 않은 정보 표시
- 일부 데이터만 제공되는 경우

날짜·시간·통화·단위와 다국어 용어의 표기 규칙은 12.5절에서 검토한다.

<a id="checks-12"></a>

<a id="checks-11-8"></a>

##### 11.8 정보 위계와 화면 밀도

- 핵심 정보와 주요 행동이 쉽게 발견되는가?
- 현재 작업과 관련 없는 정보·장식·모션이 집중과 작업을 방해하지 않는가?
- 정보를 줄이거나 접었을 때 필요한 내용·도움말·진입점까지 숨기지 않았는가?
- 긴 콘텐츠와 복잡한 기능에서도 그룹·순서·강조로 정보 우선순위를 구분하는가?

#### 12. 사용자 커뮤니케이션 및 UX 라이팅 (User Communication & UX Writing)

사용자에게 질문하거나 정보를 전달할 때 메시지의 목적, 표현 방식, 어투 및 행동 유도 방법을 검토한다.

**적용 범위:** 사용자에게 텍스트, 음성, 알림 등으로 정보를 전달하는 모든 UI

##### 12.1 사용자에게 질문하거나 행동을 요청하는 경우 (Action Required)

- 필수 정보 입력 요청
- 선택 항목 지정 요청
- 사용자 의도 재확인
- 중요한 작업의 확인 요청에서 결과·위험·확인 및 취소 선택지를 어떻게 표현할지 검토. 삭제 방식·복구 조건은 [삭제](#checks-4)에서 정의한다.
- 추가 권한 요청
- 로그인 또는 인증 요청
- 다음 단계로 진행하도록 행동 유도
- 사용자가 취해야 할 행동을 명확하게 안내
- 확인·취소 버튼의 의미가 명확한지 검토
- 사용자가 응답하지 않거나 요청을 취소한 경우 처리

##### 12.2 사용자에게 정보를 안내하는 경우 (Informational Messages)

- 일반 정보 및 공지 안내
- 사용자 행동에 대한 즉각적인 피드백
- 작업 완료 안내
- 저장 완료 또는 자동 저장 상태 안내
- 정보 변경 및 업데이트 안내
- 주의 사항 및 경고 안내
- 별도 행동이 필요 없는 알림과 행동이 필요한 알림 구분

진행 상황 안내는 12.3절, 작업 실패·오류 안내는 10절에서 검토한다.

<a id="checks-12-3"></a>

##### 12.3 로딩 및 진행 상황 안내 (Loading & Progress Feedback)

사용자가 작업을 요청했을 때 예상 대기 시간, 진행률 측정 가능 여부, 콘텐츠 유형, 작업의 중요도에 따라 적절한 로딩 UI와 모션을 정의한다.

###### 로딩 UI 유형별 사용 기준

아래 항목은 배타적인 선택지가 아니다. 표시 형태(스피너·스켈레톤·프로그레스 바·단계 표시·메시지), 표시 위치(버튼 내부·콘텐츠 영역·화면 상단 등), 처리 방식(현재 작업에서 대기·백그라운드 처리)을 구분해 조합한다. 예를 들어 백그라운드 업로드에 프로그레스 바와 상태 메시지를 함께 사용할 수 있다.

| UI 유형 | 권장 사용 상황 | 예시 |
| --- | --- | --- |
| 로딩 표시 없음 | 즉시 완료되는 작업. 로딩 표시가 오히려 화면을 깜빡이게 할 때 | 즉각적인 탭 전환 |
| 스피너 (Spinner) | 진행률을 알 수 없는 짧은 작업 | 검색 요청, 간단한 데이터 저장 |
| 스켈레톤 (Skeleton) | 화면의 구조를 예측할 수 있고 콘텐츠를 불러오는 중일 때 | 게시물 목록, 상품 카드, 프로필 |
| 프로그레스 바 (Progress Bar) | 진행률을 측정할 수 있는 작업 | 파일 업로드, 다운로드, 데이터 처리 |
| 불확정 프로그레스 바 (Indeterminate Progress Bar) | 진행률은 알 수 없지만 작업이 진행 중임을 선형으로 표시할 때 | 화면 상단의 페이지 로딩 표시 |
| 버튼 내부 로딩 (Button Loading) | 사용자가 실행한 버튼의 작업이 처리 중일 때 | 저장, 제출, 결제 요청 |
| 단계별 진행 표시 (Step Progress) | 여러 단계로 이루어진 작업의 현재 단계를 보여줄 때 | 회원가입, 데이터 가져오기 |
| 진행 상태 메시지 (Status Message) | 작업이 오래 걸리거나 현재 처리 단계를 설명해야 할 때 | AI 콘텐츠 생성, 대량 데이터 처리 |
| 백그라운드 작업 표시 (Background Task) | 사용자가 다른 작업을 계속할 수 있을 때 | 대량 이미지 변환, 파일 내보내기 |

###### 로딩 시간에 따른 추가 고려사항

- 약 0~1초: 불필요한 로딩 UI 노출 최소화
- 약 1~3초: 스피너, 스켈레톤 등 간단한 피드백 고려
- 약 3초 이상: 진행 상태 안내 및 사용자 불안 감소 방안 검토
- 장시간 작업: 진행률, 현재 단계, 예상 소요 시간, 취소 기능 검토
- 실제 진행률을 알 수 없는 경우 임의의 퍼센트 표시 방지
- 예상 소요 시간을 신뢰성 있게 계산할 수 있는 경우에만 남은 시간 표시

※ 시간은 절대적인 규칙이 아니라 참고 기준이다. 로딩 UI의 종류는 작업 특성과 진행률 측정 가능 여부를 우선하여 결정한다.

###### 로딩 UI 설계 체크리스트

- 로딩 시작 시점 정의
- 위 유형별 사용 기준에 따른 로딩 UI 선택
- 로딩 UI 표시 위치 정의
- 로딩 중 사용자 조작 허용 여부와 버튼의 처리 중 표시·비활성화 결정. 요청 중복에 대한 실제 처리 정책은 [작업 중단 및 복구](#checks-10-5)에서 검토한다.
- 로딩 완료 시 UI 전환 방식
- 로딩 실패 및 시간 초과 처리
- 로딩 애니메이션의 움직임과 속도 정의
- 모션 감소 설정을 사용하는 사용자를 위한 대체 표현
- 로딩 상태를 보조 기술에도 전달

<a id="audit-process"></a>

## 3부. 제작 중·후 — UX Audit와 개선안 작성

실제로 만들어진 화면과 동작을 확인하는 절차다. 문서에 적혀 있는 정책, 소스 구현, 자동 테스트, 실제 브라우저·기기 확인을 구분하고 관찰 근거 없이 완료로 판정하지 않는다.

### 0. 분석 목적

현재 웹사이트가 필요한 사용자 상황에 대응하도록 설계·구현되어 있는지 확인하고, 실제 이용을 방해하는 문제와 개선안을 찾는다. 가능한 시나리오의 수를 늘리는 것 자체를 목표로 삼지 않는다.

- 예외 대응은 [공통 UI 상태](#checks-8), [오류·복구](#checks-10), [콘텐츠 표시](#checks-11), [메시지 표현](#checks-12)의 상세 항목으로 확인한다.
- 정상 흐름의 사용성은 아래 [닐슨 평가 연결표](#section-16)로 판단한다. 질문은 해당 상세 항목 한 곳에서 관리하고, 같은 문제를 체크리스트별로 중복 등록하지 않는다.

### 1. 분석 범위

전체 프로젝트를 한 번에 상세 분석하지 않는다.

점검을 시작할 때 사용자가 지정한 메뉴·기능·화면과 제외 범위를 먼저 명시한다.

- 지정한 범위에 속한 하위 페이지, 기능, 실제 사용자 흐름을 분석한다.
- 해당 기능과 직접 연결된 로그인·권한·데이터 저장 등 공통 기능은 필요한 범위에서 함께 검토한다.
- 지정하지 않은 다른 메뉴로 분석을 임의 확장하지 않는다.
- 예를 들어 레시피 메뉴를 지정했다면 목록·상세·등록·수정·삭제를 점검한다. 레시피는 적용 예시이며 다른 웹사이트에도 범위를 정해 사용할 수 있다.

먼저 해당 메뉴의 하위 화면과 주요 기능을 파악한 다음, 각 화면의 현재 구현 상태를 분석한다.

다음 자료를 참고한다.

- docs/requirements.md
- 실제 프로젝트의 메뉴·페이지 구조 문서 또는 구조 데이터
- 이 문서의 제작 전 검토 결과와 공통 상세 체크리스트
- docs/design-system.md
- 실제 프런트엔드 코드
- 관련 백엔드 및 API 코드(접근 가능한 경우)
- 실제 실행 화면(확인 가능한 경우)

범위에 맞는 정책·코드·화면·테스트 근거를 수집한다. 검증하지 못한 동작은 [판정 기준](#3-대응-상태-판정)에 따라 ‘확인 필요’로 남긴다.

### 2. 진단 기준

다음 5가지 범주를 점검 기준으로 활용한다.

1. Normal & Alternative Flows
2. Error & Exception Cases
3. Edge & Boundary Cases
4. UI & System States
5. Security & Abuse Cases

각 범주에 속하는 시나리오를 무조건 많이 만들 필요는 없다.

실제 사용자 경험에 영향을 주는 중요한 상황을 우선 검토한다.

각 상황에 대해 다음 질문에 답한다.

1. 해당 상황에 대한 대응이 필요한가?
2. PRD 또는 디자인 시스템에 대응 정책이 정의되어 있는가?
3. 실제 코드에 대응 로직이 구현되어 있는가?
4. 사용자에게 적절한 UI와 메시지가 제공되는가?
5. 현재 대응 방식에 UX 문제가 있는가?
6. 개선이 필요하다면 무엇을 어떻게 변경해야 하는가?

<a id="section-16"></a>

#### 사용성 평가 연결표 — 닐슨의 10가지 휴리스틱

2부는 설계·구현할 행동과 상태를 정리하는 질문이고, 이 표는 그 설계가 실제 사용자에게 적절한지 판단하는 관점이다. 같은 질문을 다시 작성하지 않고 연결된 항목을 근거로 평가한다. UI 설계·프로토타입·QA에서 필요한 화면과 컴포넌트에 적용한다.

| 번호·평가 관점 | 판단할 핵심 | 상세 질문 위치 |
| --- | --- | --- |
| H1 상태 가시성 | 행동 결과·처리 중 상태·현재 위치를 적시에 알 수 있는가? | [공통 상태](#checks-8), [진행 안내](#checks-12-3), [조회·이동](#checks-5) |
| H2 현실과 일치 | 용어·단위·정보 순서가 사용자에게 익숙한가? | [조회·정보 순서](#checks-5), [보이스톤](#checks-12-4), [표기·용어](#checks-12-5) |
| H3 사용자 통제 | 취소·이탈·복구가 가능하고 의도하지 않은 손실을 막는가? | [생성](#checks-2), [수정](#checks-3), [삭제](#checks-4), [중단·복구](#checks-10-5) |
| H4 일관성과 표준 | 같은 역할이 같은 표현·동작으로 제공되는가? | [디자인 방향](#section-09), [표기·동작 일관성](#checks-12-5), 디자인 시스템 |
| H5 오류 예방 | 실수·위험한 실행·중복 요청을 미리 막는가? | [입력 오류](#checks-10-1), [삭제](#checks-4), [중단·복구](#checks-10-5) |
| H6 기억보다 인식 | 현재 선택·필터·필드 목적·도움말을 기억에 의존하지 않고 확인하는가? | [선택](#checks-1), [조회·정보 순서](#checks-5), [도움말](#checks-6), [입력 안내](#checks-10-1) |
| H7 유연성과 효율성 | 초보자는 쉽게, 숙련자는 반복 작업을 효율적으로 수행하는가? | [조회·작업 효율](#checks-5), [선택·일괄 작업](#checks-1), [입력 방식](#checks-9) |
| H8 간결한 디자인 | 핵심 정보는 드러내고 불필요한 복잡함은 줄였는가? | [정보 위계·밀도](#checks-11-8), [콘텐츠 양](#checks-11-6) |
| H9 오류 이해·복구 | 문제 위치·원인·해결 행동을 이해하고 작업을 이어갈 수 있는가? | [오류·복구](#checks-10), [문구 품질](#checks-12-7), [메시지 표시](#checks-12-6) |
| H10 도움말 | 현재 작업에 맞는 설명·예시·문의 수단에 접근할 수 있는가? | [도움말·지원](#checks-6), [정보 위계·진입점](#checks-11-8) |

결과는 다음 판정 기준을 적용한 뒤 [문제 기록 양식](#4-ux-문제-발견-및-개선안)에 한 번만 남긴다. 같은 문제에 여러 휴리스틱이 관련되면 동일 ID에 H1·H9처럼 함께 연결한다.

### 3. 대응 상태 판정

각 점검 항목에 다음 상태를 부여한다.

- 적절함: 필요한 대응이 정의·구현되어 있고 확인 가능한 범위에서 UX 문제가 없음
- 개선 필요: 대응은 존재하지만 UX 또는 처리 방식에 문제가 있음
- 누락: 필요한 대응이 정의되거나 구현되지 않음
- 확인 필요: 자료가 부족하여 판단할 수 없음
- 해당 없음: 현재 기능과 관련 없는 상황

PRD에 정의되어 있지만 구현되지 않은 경우와, 구현되어 있지만 PRD에 정의되지 않은 경우를 구분하여 기록한다.

실제 확인하지 않은 동작을 정상이라고 추정하지 않는다.

### 4. UX 문제 발견 및 개선안

문제는 하나의 ID로 관리하고 아래 내용을 기록한다. 다른 체크리스트나 휴리스틱에서 같은 원인을 발견해도 별도 문제로 중복 집계하지 않는다. 원인·해결 방법·담당 작업이 다르면 각각 기록한다.

| 기록 항목 | 포함할 내용 |
| --- | --- |
| ID·대상 | 메뉴·화면·컴포넌트·사용자 흐름 |
| 관련 기준 | 상세 체크 항목, 진단 범주, 해당하는 H1–H10 번호, PRD·디자인 시스템 근거 |
| 현재 상태·근거 | 실제 화면과 동작, 코드 파일·위치, 테스트 및 관찰 조건 |
| 문제·사용자 영향 | 부족하거나 잘못된 점과 불편·위험. 관찰 사실과 추정을 구분 |
| 판정 | 3절의 상태. 정책 미정의와 구현 누락을 구분 |
| 심각도·우선순위 | 필요한 경우 사용성 심각도 0–4 및 아래 P0–P2. 두 값을 구분 |
| 구체적인 개선안 | 화면 구조·UI·문구·처리 로직·재시도·취소·복구·입력 보존 방법. 기존 디자인 시스템과 Carbon 컴포넌트 우선 활용 |
| 조치·검증 상태 | 미조치 / 개선 예정 / 개선 완료 / 해당 없음. 승인 여부와 검증 방법·결과·한계도 함께 기록 |

**사용성 심각도:** 0 문제 아님 / 1 경미 / 2 보통 / 3 심각 / 4 치명적. 출시 차단 여부는 프로젝트 정책과 사용자 승인에 따른다. 체크 표시·개선안 작성·코드 반영만으로 실제 검증 완료를 표시하지 않는다.

### 5. 우선순위

- P0: 보안 문제, 데이터 손실, 핵심 기능 중단 등 치명적인 문제
- P1: 주요 작업 수행에 지장을 주거나 심각한 사용성 문제를 유발하는 경우
- P2: 상대적으로 영향이 작지만 개선할 가치가 있는 문제

심각도 0–4는 사용성 문제의 정도이고 P0–P2는 개선 작업의 처리 우선순위다. 자동으로 대응시키지 않고 사용자 영향과 데이터·보안 위험을 함께 판단한다. 정상 구현·해당 없음에는 개선 우선순위를 부여하지 않는다.

### 6. 출력 형식

#### A. 분석 범위 요약

분석한 메뉴, 하위 화면, 주요 기능을 먼저 제시한다.

#### B. 진단 요약

- 점검 항목 수
- 적절함
- 개선 필요
- 누락
- 확인 필요
- 해당 없음

#### C. 문제 및 개선안

‘개선 필요’ 또는 ‘누락’ 항목을 중심으로 [4절의 기록 양식](#4-ux-문제-발견-및-개선안)을 표로 정리한다. 문제 수는 고유 ID 기준으로 집계한다. 개선 UI·실제 문구·복구 흐름 등 긴 설명은 같은 ID 아래에 덧붙인다.

#### D. 정상 대응 항목

이미 적절하게 구현된 항목은 간단히 요약한다.

정상 대응 항목을 문제 목록에 반복해서 작성하지 않는다.

#### E. 확인이 필요한 항목

실제 화면 테스트나 추가 정책 결정이 필요한 사항을 별도로 정리한다.

### 7. 작업 순서

1. 지정한 메뉴와 관련된 문서 및 코드를 분석한다.
2. 해당 메뉴의 화면과 기능 목록을 작성한다.
3. 중요한 사용자 흐름과 예외 상황을 점검한다.
4. 현재 대응 정책과 실제 구현 상태를 확인한다.
5. UX 문제와 대응 누락을 발견한다.
6. 문제의 심각도에 따라 우선순위를 부여한다.
7. 구체적인 UI·메시지·동작 개선안을 제안한다.
8. 내가 검토하고 승인할 때까지 기다린다.

**내 승인 전에는 PRD, 디자인 시스템, 소스코드 등 어떤 파일도 수정하지 않는다.**

최종 산출물은 6절의 진단 보고서이며, 검토 대상 시나리오 목록만 제출하고 끝내지 않는다.

## 문서 저장·관리 규칙

- 통합 체크리스트·Audit 가이드와 점검 결과는 `docs/checklist-audits` 한 폴더에서 관리하며 메뉴별 하위 폴더를 추가하지 않는다.
- 가이드는 사용자 지정 이름인 `checklist-audit-guide.md`로 유지한다. 날짜가 있는 기록은 `YYYY-MM-DD-문서유형-상세주제.md` 순서로 이름을 짓는다. 점검 결과는 `results`, 요약은 `summary`처럼 실제 내용에 맞는 문서유형을 날짜 바로 뒤에 둔다. 예: `2026-10-28-results-nav-recipes.md`, `2026-11-10-results-design-system-spacing.md`. 생성일과 본문의 분석 기준일이 다르면 두 날짜를 구분해 기록한다.
- 새 결과는 루트 `README.md`의 문서 목록에 링크·범위·상태를 추가한다. 재진단은 새 날짜 파일을 만들고 기존 결과를 보존한다.
- 보고서는 [출력 형식](#6-출력-형식)의 A~E 순서로 작성하고, 세부 필드는 [문제 기록 양식](#4-ux-문제-발견-및-개선안)을 따른다.
- 최초 진단은 검토 대기다. 승인 정책은 `docs/requirements.md`, 공통 UI 규칙은 `docs/design-system.md`, 사이트별 예외는 `docs/design-system-project.md`에서 관리하고 보고서에서는 연결한다.
- 진단 작성만으로 구현·운영 데이터 변경·배포까지 승인된 것으로 처리하지 않는다. 과거 기록의 날짜는 최신 구현·검증·배포일을 뜻하지 않는다.
- 메뉴 구조의 원본·도식·검증 도구는 `docs/navigation`에, 구조 점검 결과는 이 폴더에 둔다.
