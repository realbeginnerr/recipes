# IA 리뷰 — 2026-10-19

## 1. 분석 개요

현재 작업 디렉터리의 `src/App.tsx`, `main.tsx`, 헤더/푸터/Layout, pages, 공유 UI, 인증 context와 접근 provider, 서비스 및 Firestore/Storage 규칙을 정적으로 분석했다. 라우트 19개 중 페이지 17개, redirect 2개다. As-Is 44개 노드, To-Be 45개 노드이며 최대 depth는 모두 4다.

운영 사이트 실행·분석 이벤트 데이터·사용자 테스트는 수행하지 않았다. 아래 구조 사실과 그로 인한 사용성 가설을 분리한다. 빈도·이탈률·전환율은 추정하지 않는다. 초판 분석에서는 제품 코드를 변경하지 않았다. 2026-10-19에 사전 신청 기능을 삭제하고 현재 구조에 맞춰 이 문서를 갱신했다. 운영 배포와 DB 데이터 삭제는 수행하지 않았다.

레시피 추가는 방식 선택 화면 없이 작성 폼으로 바로 진입한다. SNS 입력·AI 프롬프트·답변 붙여넣기는 제거했다. 식재료 추가도 수정과 동일한 공통 폼으로 바로 진입하며 정보·영양·단위 환산을 입력한다. 식재료 AI 입력 기능은 제거했다. 공개 식재료 목록 표에는 열별 정렬도 있다. 단순 열 제어는 독립 IA 노드로 확장하지 않았다.

모바일은 768px 미만에서 동일 링크를 접힘 nav로 제공한다. GNB 정보 목록은 논리적으로 같고 별도 drawer가 아니다. 레시피 이미지 확대는 모바일 표시 조건이 있다. 표의 가로 스크롤·메뉴 키보드 동작·실제 화면 가독성은 기기에서 확인해야 한다.

## 4. 확인된 구조적 문제

### IA-01 — 공개 페이지의 내부 진입 부재

- 관련 ID: roulette, eating-guide, shop
- 사실/근거: SiteHeader.tsx GNB는 홈/레시피/식재료뿐이고 footer에 링크가 없다. 전체 src 내 링크/이동 코드 검색에서 `/recipe-roulette`, `/eating-out`으로 진입하는 링크를 확인하지 못했다. Shop은 관리자 상품 화면 복귀 링크로 접근 가능하므로 완전한 고립으로 분류하지 않는다.
- 영향 가설: URL을 모르는 공개 사용자가 도구/안내/상품 영역을 발견하기 어려울 수 있다. 실제 발견률은 미측정이다.
- 심각도: Medium. 우선순위 P1.
- 제안: 레시피 목록에 룰렛 진입, 홈에 관련 안내 영역, Shop GNB 항목을 제안한다. 서비스 운영 의도에 따라 숨겨둔 페이지는 공개 확대 대신 정리할 수 있다.
- 검증 필요: 예. 의도적으로 비노출한 화면인지, 유입 경로/외부 링크가 있는지 운영자 확인 및 발견 과제 테스트.
- 검토 상태: 룰렛·식사 가이드의 진입 링크 경고 2개를 미해결 항목으로 유지한다. 비노출이 의도된 결정이라는 근거는 아직 없으므로 정상 또는 접근 불가로 단정하지 않는다. To-Be의 문맥 링크는 개선 제안이며 운영 적용 결정은 보류한다.

### IA-03 — Shop의 이름·URL·분류 체계 혼재

- 관련 ID: shop, shop-discovery, product-detail
- 사실/근거: RecipePage.tsx blendingTea 분기 제목은 Shop, URL은 `/blending-tea`, itemLabel/일부 빈 상태는 차, 필터는 전체/에코백/기타다. 차 레시피와 상품을 함께 가져오며 카드의 목적 URL도 recipe/product로 갈린다. SiteHeader.tsx에는 Shop 항목이 없다.
- 영향 가설: 목록의 범위와 카드 선택 후 나올 정보를 예상하기 어려울 수 있다.
- 심각도: Medium, P1.
- 제안: 우선 공개 진입을 명확히 하고 상품 범위/용어를 운영자와 확정한다. URL 교체나 차 전용 카테고리 확정은 보류한다.
- 검증 필요: 예. 실제 등록 데이터의 구성과 카테고리 정합성, 명칭 이해 테스트.

### IA-04 — 제보 작성 UI와 공개 역할의 불일치

- 관련 ID: ingredient-report, ingredient-reports, ingredients-list
- 사실/근거: 제보 작성 모달은 현재 관리자 화면 안에 있다. 공개 식재료 목록에서는 해당 모달이 렌더되지 않는다. 제보 주체와 화면 진입·접근 정책의 정합성 확인이 필요하다.
- 영향 가설: 일반 사용자의 오류 제보가 의도된 요구사항이라면 진입을 찾을 수 없다. 현재 요구가 관리자 내부 기록이라면 결함이 아닐 수 있다.
- 심각도: Low, P2.
- 제안: 제보 주체를 확정한다. 공개 제보 진입은 미결정 제안으로만 보관하고 현재 access를 완화하지 않는다.
- 검증 필요: 예. 제보 운영 목적과 스팸/처리 흐름 확인.

### IA-06 — 사용 중 식재료 경고의 레시피 링크 불일치

- 관련 ID: ingredient-delete-warning, recipe-detail
- 사실/근거: IngredientManagementPage.tsx의 삭제 경고 링크는 `/recipes/#${r.id}`다. 현재 상세 라우트는 `/recipe/:id`, 앱 basename은 `/recipes/`이므로 이 href는 배포 홈과 해시로 이동한다. 현재 레시피 목록/상세에는 이 해시를 해석하는 로직이 없다.
- 영향 가설: 삭제 전 관련 레시피를 검토하는 관리자의 의도와 다른 위치로 이동할 수 있다.
- 심각도: Medium, P1.
- 제안: 후속 구현에서 현재 router/base 경로 규칙에 맞춰 관련 상세 진입을 통일한다. IA 노드/URL 변경은 필요 없다.
- 검증 필요: 예. 배포 환경에서 실제 링크 클릭 확인.

## 5. UX 개선 가설

### IA-05 — 복귀 동작과 탐색 상태 보존

- 관련 ID: recipe-detail, recipes, recipe-edit, product-detail
- 근거: BackLink.tsx의 한국어 '뒤로가기'는 브라우저 뒤로가기가 아닌 `/recipes` 링크다. 공개 정상 레시피 상세에는 이 링크가 없고 실패 상태에서만 나타난다. 레시피 편집은 `navigate(-1)`, 상품 관리 복귀는 Shop 고정이다. q/ingredient는 URL, 카테고리/정렬/목록 확장량은 로컬 상태다.
- 영향 가설: 상세에서 이전 탐색 조건으로 돌아오거나 직접 진입 후 복귀할 때 기대가 다를 수 있다. 불필요한 탐색 횟수는 측정하지 않았다.
- 심각도: Medium, P2.
- 제안: '목록으로'와 '이전 화면' 목적을 구분하고 보존할 필터를 합의한다. 신규 화면/경로는 확정하지 않는다.
- 검증 필요: 예. 필터 → 상세 → 복귀, 새 탭/직접 URL 진입 과제.

### IA-07 — Contact의 목적지

- 관련 ID: mobile-navigation, site (navigation.external)
- 근거: SiteHeader.tsx의 Contact에 설정된 외부 목적지가 공개 문의 목적에 맞는지 확인이 필요하다. 구체적인 외부 관리 주소는 제출 문서에서 생략한다.
- 영향 가설: 공개 문의를 예상한 사용자가 Linktree 관리 화면/로그인 요구를 만날 수 있다. 외부 서비스 실제 응답은 확인하지 않았다.
- 심각도: Low, P2.
- 제안: 운영자가 의도한 공개 문의 주소인지 확인 후 별도 변경을 결정한다.
- 검증 필요: 예. 비로그인 브라우저에서 외부 링크 확인.

### IA-08 — 알 수 없는 URL과 상태 구분

- 관련 ID: site, ingredients, recipe-edit
- 근거: App.tsx의 `*`는 홈 redirect로 전용 404가 없다. IngredientsPage.tsx는 loading 중 visible 0에서도 빈 상태를 표시할 수 있다. RecipeManagementPage.tsx 로드 실패는 console.error로 처리한다.
- 영향 가설: 주소 오류/로딩/실제 빈 데이터의 차이를 파악하기 어려울 수 있다.
- 심각도: Low, P2.
- 제안: 오류·로딩·빈 결과 안내를 점검한다. 별도 404 페이지 신설은 사용자 검증 전 확정 IA에 넣지 않는다.
- 검증 필요: 예. 네트워크 지연·오류·존재하지 않는 ID/경로 과제.

## 7. To-Be 제안 근거

기존 44개 ID, 모든 페이지 URL과 권한을 유지한다. 신규 노드는 홈의 `home-resources` section 1개뿐이다. 룰렛을 레시피 하위로, 식사 가이드를 홈 관련 정보 하위로 이동하는 구조를 제안한다. 기존 화면은 implemented, 이동/신규 진입은 planned로 분리한다. Shop은 GNB에 제안하되 아직 미구현이다.

제안의 목적은 발견 가능한 문맥을 제공하는 것이다. 모든 화면을 GNB로 올리거나 폴더명대로 재편하지 않는다. IA-06처럼 화면 관계를 유지한 채 링크를 고칠 항목은 구조 변경으로 억지 반영하지 않는다. 변경은 `ia-to-be.yaml`의 changes와 `ia-changelog.md`에서 비교한다.

## 8. 사람이 추가 확인할 항목

1. 룰렛/가이드/Shop 비노출이 의도인지, 어떤 화면을 운영할지 확정.
2. 비회원·허용 관리자·비허용 Google 계정으로 직접 URL/로그인/취소/로그아웃 확인.
3. 화면 노출 정책과 데이터 접근 정책의 정합성, 실제 배포 설정을 확인. 상품 공개 시작 시각은 `publicAfter` 기준이며 `publicUntil`로 기재했던 초판 표현을 바로잡았다.
4. 실제 상품·차 레시피·카테고리 데이터로 Shop의 필터/이동 확인.
5. 모바일 메뉴, 표 스크롤, 이미지 확대, 필터 후 상세/복귀 과제 수행.
6. 배포 basename 아래 직접 URL 진입/새로고침을 GitHub Pages에서 확인.
7. Mermaid 렌더링과 FigJam 편집 가능한 카드 변환을 실제 계정에서 확인.

자동 대조 결과: 페이지 URL 및 라우트 가드 기반 권한 불일치 없음. 고립 후보 2개는 남겨둔다. 동적 URL 후보는 링크 존재의 코드 증거이며 실행 성공의 증거가 아니다. 구조 검증 통과를 실제 UX 품질 검증으로 해석하지 않는다.
