# 계층 계약 — 무엇이 무엇을 담고, 담는 그릇이 어떻게 늘어나는가 (design-dna)

> 이 문서는 **"그릇과 내용물의 계약"** 하나만 다룬다. 어떤 노드가 어떤 노드를 담을 수 있고, 담는 쪽이 담기는 쪽에 따라 **늘어나는가 잠기는가**를 규정한다.
> 무엇을 묶을지(의미단위 그룹화)·왜 이 모양인지(조형)는 `02-grouping-layout.md`, 글자 크기 위계는 `03-typography.md`, API 호출 함정은 `figma-mcp.md`·`troubleshooting.md`로 라우팅한다.
> `02`가 "묶어라"라면 이 문서는 "묶은 그릇이 어떻게 반응해야 하는가"다. 둘은 짝이다.

---

## 0. 대전제 — 왜 계약이 필요한가

정본 3개 파일을 전수 실측한 결과, **내용이 잘려 안 보이는 사고 전건이 "세로 높이를 잠근 그릇"에서 발생했고, "내용에 맞춰 늘어나는 그릇"에서는 단 한 건도 발생하지 않았다.**

| 그릇의 세로 설정 | 실측 사고 건수 | 판정 |
|---|---|---|
| 내용 따라 늘어남(hug) | **0건** | **표준** |
| 높이 잠금(fixed) | **4건** (전부 잘림) | 연출 목적일 때만, 선언 필수 |

(실측: 리뷰카드 텍스트컬럼·중간 래퍼 2종 등 3건 — 필요 높이보다 낮게 잠겨 아래가 잘리는 사고. 반대로 전 프레임 hug 관행인 사례는 사고 0건. 클라이언트 식별자는 출고본에서 제거함: <fileKey 제거>)

**원칙: 글자가 들어가는 그릇은 내용에 맞춰 늘어난다.** 높이 잠금은 배경 사진 위에 글자를 얹는 연출 캔버스에서만 허용하고 의도를 이름에 남긴다(§6).

**왜 이게 반복 사고가 되나:** 만들 때는 내용이 딱 맞으므로 잠근 높이가 정확해 보인다. 사고는 나중에 **카피가 한 줄 늘거나 폰트가 커질 때** 터지고, 그때는 이미 검수가 끝난 뒤다. 그래서 "지금 맞는가"가 아니라 "늘어날 수 있는가"로 판정한다.

## 1. 5단 계층과 계층별 사이징 계약

`02` §1의 3단 기본형(섹션→의미단위→row)을 실측 구조에 맞춰 5단으로 세분한다. 실측 계층 깊이는 4~6단이고 7단을 넘는 곳은 없었다.

```
섹션        ← 화면 하나. 캔버스 직속 개별 프레임
  영역      ← 섹션 안의 한 덩어리 (제목존, 카드묶음, 표 전체)
    카드    ← "한 가지 이야기" 단위 (리뷰 1개, QA 1쌍, 표의 한 행)
      행    ← 나란히 읽히는 짝 (마커+글, 라벨+값, 아이콘+라벨)
        잎  ← 텍스트·이미지·도형
```

### 계층별 사이징 계약표

**가로/세로를 따로 읽는다.** 가로는 "부모 폭을 채우는가(fill) / 내용만큼인가(hug) / 값을 박는가(fixed)", 세로는 "내용 따라 늘어나는가(hug) / 잠그는가(fixed) / 형제 높이를 따라가는가(fill)"다.

| 계층  | 가로 | 세로 | 왜 | 실측 빈도 |
|---|---|---|---|---|
| **섹션** | 캔버스 폭 고정 | **hug** | 캔버스에 오토레이아웃이 없으므로 폭은 값으로 박고, 세로만 내용에 맡긴다 (→`02` §0) | 세브 14중 12·크몽 7중 5가 hug |
| **영역 래퍼** | **fill** | **hug** | 좌우는 섹션 안쪽 폭을 그대로 받고, 세로는 자식 합계를 그대로 옮긴다. 이 조합이 계층 전체의 기본값 | 3파일 최빈 조합 (세브 75·크몽 48·클라이언트 A 108) |
| **카드** | fill 또는 고정폭 | **hug** | 카드 폭은 열 구성이 정하지만 높이는 언제나 내용이 정한다 | 클라이언트 A FAQ 카드 전량 |
| **행** | **fill** | **hug** | 행은 좌우로 꽉 차고, 높이는 행 안에서 가장 긴 칸이 정한다 | 3파일 표·리스트 전량 |
| **행 안 · 폭이 정해진 칸**(라벨열·마커·아이콘) | **고정폭** | **fill** | 폭은 열 규격이라 박고, 높이는 **형제가 정한 행 높이를 따라간다**. 그래야 구분선·배경이 행 끝까지 닿는다 | 클라이언트 A 제품표 라벨셀·세로선 전 행 |
| **행 안 · 늘어나는 칸**(값·본문) | **fill + grow** | **hug** | 남는 폭을 이 칸이 전부 먹고, 이 칸의 높이가 곧 행 높이가 된다 | 클라이언트 A 제품표 값셀 전 행 |
| **이미지 슬롯** | **fill** | **고정** | 폭은 레이아웃이 정하고 높이만 규격으로 잡는다. 원본 이미지 크기를 프레임 크기로 삼지 않는다 | 클라이언트 A·세브 공통 패턴 |
| **텍스트 잎** | 역할이 정함 | **hug** | §5 참조 | — |

**핵심 한 줄: 행 높이는 "늘어나는 칸"이 정하고, "폭이 정해진 칸"이 그것을 따라간다.** 반대로 잡으면(라벨열이 높이를 정하게 두면) 값이 길어질 때 넘친다.

**분기 — fill이냐 hug냐 헷갈릴 때:** "이 그릇의 폭을 부모가 정해주나, 내가 정하나?"를 묻는다. 부모가 정해주면 fill, 내용이 정하면 hug다. **fill은 부모가 오토레이아웃일 때만 의미가 있다** — 오토레이아웃이 아닌 부모 밑의 fill은 아무 일도 하지 않는다(실측: 세컨드브레인 542노드 중 그런 모순 0건 — 잘 만든 파일의 지표).

## 2. 반복 사고 5종 — 증상·원인·정답

> 아래는 전부 실측에서 실제로 잡힌 것들이다. **정답 패턴만 코드로 적는다** — 틀린 값을 예제로 적으면 그 값이 그대로 재현되기 때문이다.

### 2-1. 글자 그릇의 높이 잠금 → 아래가 잘림
**증상·원인:** 카피가 한 줄 늘면 자식 합계+간격+상하패딩이 잠근 높이를 넘고, 넘친 만큼이 잘려 렌더된다. 화면에서는 "글이 짧아 보이는" 것으로만 나타나 발견이 늦다(세로 정렬이 가운데면 위아래로 나뉘어 더 안 띈다).
**정답:** 글자를 담는 모든 그릇은 세로 hug로 만든다.
```js
frame.layoutMode = 'VERTICAL';
frame.primaryAxisSizingMode = 'AUTO';    // 세로 = 내용 따라
frame.counterAxisSizingMode = 'FIXED';   // 가로 = 부모가 준 폭
frame.layoutSizingHorizontal = 'FILL';
```

### 2-2. 부모 안쪽 폭보다 넓은 자식 → 좌우가 잘림
**증상·원인:** 자식에게 부모의 **바깥 폭**을 그대로 줬으나 실제로 쓸 수 있는 건 **안쪽 폭(부모 폭 − 좌우 패딩)**이라 좌우 끝이 잘린다. 가운데 정렬이면 양쪽이 똑같이 잘려 "원래 저런 디자인"처럼 보인다.
**정답:** 자식 폭을 값으로 계산하지 말고 부모에게 맡긴다 — `child.layoutSizingHorizontal = 'FILL'`이 안쪽 폭을 자동으로 받는다. 폭을 꼭 박아야 하면 `부모.width − 부모.paddingLeft − 부모.paddingRight` 이내로만 잡는다.

### 2-3. 배경 이미지를 흐름 자식으로 넣기 → 부모가 밀려 내용이 잘림
**증상·원인:** 오토레이아웃은 자식을 순서대로 쌓으므로, 섹션만 한 배경이 흐름 안에 있으면 그 뒤 형제가 전부 아래로 밀려 사라지거나 프레임 밖으로 나간다.
**정답:** 배경은 흐름에서 빼서 깔고 그 위에 콘텐츠를 쌓는다 — `bg.layoutPositioning = 'ABSOLUTE'`(흐름 밖, 형제를 밀지 않음) 후 `section.insertChild(0, bg)`로 맨 뒤에 둔다. (정본 사례: 클라이언트 A FAQ 섹션의 배경 사진 3종.)

### 2-4. 표의 모든 칸을 고정폭으로 → 재계산 불가·좌표 어긋남
**증상·원인:** 칸이 전부 고정폭이면 남는 폭을 아무도 흡수하지 못해, 표 폭을 바꿀 때 칸이 어긋나고 좌표가 소수점으로 밀린다.
**정답:** 라벨열만 고정폭, 값열이 나머지를 흡수한다(§1 계약표).
```js
labelCell.layoutSizingHorizontal = 'FIXED';   // 라벨열 = 열 규격
valueCell.layoutSizingHorizontal = 'FILL';
valueCell.layoutGrow = 1;                     // 남는 폭을 전부 흡수
divider.layoutSizingVertical = 'FILL';        // 세로선이 행 높이를 따라감
```

### 2-5. 이름이 같은 형제 그릇이 둘 이상 → 수정 잔재
**증상·원인:** 고치다가 복제한 뒤 옛것을 지우지 않아 같은 이름의 리스트·카드가 나란히 두 개 남고, 하나만 최신이다(실측: 크몽 파일 동명 리스트 컨테이너 2개).
**정답:** 같은 부모 밑에 같은 이름이 둘이면 어느 쪽이 정본인지 확인한 뒤 하나만 남긴다. 반복 카드처럼 **의도적으로 같은 종류가 N개**인 경우는 이름에 구분자를 붙인다(`리뷰카드_이*미`·`QA유닛1`처럼 — `02` §6 네이밍 규칙).

## 3. 여백 생성 표준 — 패딩과 간격만

**규칙: 여백은 패딩, 항목 사이는 간격(itemSpacing). 빈 프레임을 끼워 밀지 않는다.**
(실측: 3개 파일 전수 검색 결과 스페이서·여백 용도의 빈 노드 **0건** — 이미 확립된 관행이다.)

| 만들 것 | 방법 | 왜 |
|---|---|---|
| 섹션 상하 여백 | 섹션 프레임의 상하 패딩 | 내용이 늘어도 여백이 유지된다. 빈 노드는 내용과 함께 밀린다 |
| 그룹·항목 사이 간격 | 부모의 itemSpacing | 항목이 추가·삭제돼도 간격이 자동 유지 (→`02` §2b 그룹 간 하한) |
| 좌우 여백 | 섹션 좌우 패딩, **한 페이지 안에서 단일값** | 섹션마다 다르면 세로로 훑을 때 가장자리가 흔들린다 (실측 클라이언트 A·크몽 모두 페이지 내 단일값, 캔버스 폭의 8% 안팎 — `02` §7의 8~10%와 일치) |
| 한쪽으로 붙이기 | 정렬(justify)로 민다 | 남는 공간을 노드로 채우지 않는다. 정본 사례: 클라이언트 A FAQ의 답변 카드가 끝 정렬로 오른쪽에 붙고, 왼쪽 빈 공간에는 아무 노드도 없다 |
| 겹침 연출 | **음수 itemSpacing** | 절대좌표로 끌어다 놓으면 내용이 바뀔 때 겹침이 어긋난다. 음수 간격은 관계로 유지된다 (실측 클라이언트 A 이미지↔타이틀 겹침) |

## 4. 리스트 행 레시피 — 마커가 첫 줄에 붙는 법

`02`의 "마커를 쓰면 텍스트 첫 줄과 광학 정렬 필수"를 실행 가능한 형태로 정리한다. **본문이 몇 줄이 될 수 있느냐**가 레시피를 정한다.

**선택 기준 한 줄: 한 줄로 끝나면 C, 여러 줄이 될 수 있으면 A, A를 못 쓰는 도형 마커면 B(공식 필수).**

### 레시피 A — 마커를 글자로 (여러 줄 · 가장 견고 · 우선)
마커를 도형이 아니라 **본문과 같은 글자크기·행간의 텍스트 노드**로 만든다. 그러면 마커의 첫 줄 높이와 본문의 첫 줄 높이가 같아져 **정렬 보정값이 아예 필요 없다.**
```js
row.layoutMode = 'HORIZONTAL';
row.counterAxisAlignItems = 'MIN';        // 위 정렬 — 첫 줄끼리 만난다
marker.fontSize = body.fontSize;          // 같은 크기
marker.lineHeight = body.lineHeight;      // 같은 행간 → 첫 줄 높이 일치
marker.textAutoResize = 'HEIGHT';
body.layoutSizingHorizontal = 'FILL';  body.layoutGrow = 1;
```
**왜 견고한가:** 글자 크기나 행간을 나중에 바꿔도 마커가 함께 따라간다. 손볼 값이 없다. (정본 사례: 클라이언트 A 제품 고지문 리스트.)

### 레시피 B — 도형 마커 + 한 줄 높이 래퍼 (여러 줄)
도형 마커를 써야 하면, 마커를 **본문 한 줄 높이만 한 래퍼** 안에 넣고 가운데에 둔다. 행이 위 정렬이므로 래퍼는 본문 맨 위에 붙고, 마커는 첫 줄의 세로 한가운데에 온다.
**공식(실측 일치 확인):** `래퍼 높이 = 본문 글자크기 × 행간비율` · `마커 y = (래퍼 높이 − 마커 높이) ÷ 2`
```js
row.counterAxisAlignItems = 'MIN';
wrapper.layoutMode = 'VERTICAL';
wrapper.primaryAxisAlignItems = 'CENTER';    // 래퍼 안에서 세로 가운데
wrapper.counterAxisAlignItems = 'CENTER';
wrapper.resize(markerSize, body.fontSize * lineHeightRatio);   // ← 공식
```
**주의:** 래퍼 높이가 잠긴 값이므로 **글자 크기나 행간을 바꾸면 이 값을 반드시 다시 계산한다.** 이 재계산을 빠뜨린 것이 마커 정렬 반복 실패의 원인이다. 재계산이 부담이면 레시피 A로 간다.

### 레시피 C — 행 세로 가운데 (한 줄 전용)
행을 `row.counterAxisAlignItems = 'CENTER'`로 두면 마커가 행 한가운데에 온다. **한 줄이 보장되는 짧은 항목에만 쓴다.** 본문이 두 줄이 되는 순간 마커가 두 줄 사이 한가운데로 떠올라 첫 줄과 어긋난다. (정본 사례: 클라이언트 A 근거 스트립, 크몽 체크 행 — 둘 다 한 줄 문구.)

## 5. 텍스트 사이징 — 역할이 설정을 정한다

**규칙: 글자의 늘어남 설정은 디자이너 취향이 아니라 그 글의 역할이 정한다.** `02` §1의 hug/fixed 판정을 Figma 설정까지 확정한 표다.

| 역할 | 설정 | 왜 |
|---|---|---|
| **제목·배지·칩 안 짧은 글** | 가로세로 모두 자동 (`WIDTH_AND_HEIGHT`) | 글자가 그릇 크기를 정하는 자리다. 배지는 내용물에 옷을 맞춘다 |
| **본문·표 값·리스트 문구** | **세로만 자동** (`HEIGHT`) + 가로는 fill/고정 | 폭은 부모가 정하고 높이만 글이 정한다. 읽는 문단은 폭이 고정돼야 가독 리듬이 유지된다 |
| **카드 높이를 맞추려 잘라내는 글** | 잘림 (`TRUNCATE`) | 의도적 잘림. **높이가 확정된 카드 안에서만** 허용하고 의도를 선언한다(§6) |

**행간 관행: 본문은 150%가 기본**(3개 파일 본문 전량), 제목·칩은 자동, 큰 숫자·마커 문구는 100~135%로 좁힌다. **레시피 B의 래퍼 높이 공식이 이 행간 위에서 성립**하므로, 본문 행간을 바꾸면 마커 래퍼도 함께 바뀐다.

**주의 — 본문에 "가로세로 모두 자동"을 쓰지 않는다:** 줄바꿈이 사라져 한 줄로 무한히 늘어난다. 이건 설정 실수가 아니라 역할 판정 실수다.

## 6. 예외 선언 규약 — 의도는 남기고, 침묵은 사고다

이 문서의 규칙 중 셋은 **의도적으로 어길 수 있다.** 다만 어겼다는 사실을 남겨야 한다.

| 예외 | 언제 허용 | 어떻게 남기나 |
|---|---|---|
| **섹션 높이 잠금** | 배경 사진 위에 글자를 얹는 연출 캔버스 | 섹션 이름에 역할을 드러낸다(`히어로`·`클로징`·`배경연출` 등) |
| **캔버스 밖 블리드** | 요소가 화면 밖으로 흘러나가는 연출 | 이름에 `블리드`·`풀블리드` 표기 (→`02` §7b의 풀블리드 배경 예외와 같은 취급) |
| **글 잘림(TRUNCATE)** | 카드 높이를 맞추려 후기·설명을 잘라낼 때 | 이름 또는 설명에 잘림 의도 표기 |

**왜 선언인가:** 검증은 수치로 판정한다. 선언이 없으면 의도된 연출과 사고를 구분할 방법이 없어, 고쳐야 할 것을 놔두거나 **멀쩡한 연출을 임의로 고치게 된다.** 후자가 더 나쁘다 — 겹침·불균형·화면 밖 배치는 의도된 연출일 수 있으므로, 선언 없는 위반을 발견하면 고치기 전에 유저에게 의도를 확인한다(→`00-interview.md`).

## 7. 기계 검증 — 완료 전 전수 판정식

**`build-recipes.md` §1 자가검증에 편입할 실행 코드.** 눈으로 스크린샷을 봐서는 잘린 글자를 못 찾는다(잘린 결과가 "원래 짧은 글"처럼 보이기 때문). 아래 4식으로 전수 대조한다. **①은 세로 오토레이아웃만 보므로 가로 오토레이아웃의 세로 잠금은 ①-b가 잡는다.** 2026-09-07 세컨드브레인 페이지 `11:106`(HORIZONTAL, 높이 480 고정, 자식 높이 504 → 24px 잘림)이 판정식을 통과해 사각지대로 실측 발견됐다.

```js
// 섹션 루트에서 실행. 반환이 빈 배열이어야 통과.
function auditHierarchy(root) {
  const issues = [], AL = n => 'layoutMode' in n && n.layoutMode !== 'NONE';
  for (const n of root.findAll(x => true).concat([root])) {
    const kids = ('children' in n)
      ? n.children.filter(c => c.layoutPositioning !== 'ABSOLUTE' && c.visible) : [];
    // ① 세로 넘침 — 잠근 높이보다 내용이 많다
    if (n.layoutMode === 'VERTICAL' && n.layoutSizingVertical === 'FIXED' && kids.length) {
      const need = kids.reduce((s, c) => s + c.height, 0)
                 + n.itemSpacing * (kids.length - 1) + n.paddingTop + n.paddingBottom;
      if (need > n.height + 1) issues.push(`세로넘침 ${n.id} "${n.name}" +${Math.round(need - n.height)}`);
    }
    // ①-b 가로 오토레이아웃의 세로 잠금 — 가장 높은 자식 + 상하패딩이 잠근 높이를 넘는다
    if (n.layoutMode === 'HORIZONTAL' && n.layoutSizingVertical === 'FIXED' && kids.length) {
      const need = Math.max(...kids.map(c => c.height)) + n.paddingTop + n.paddingBottom;
      if (need > n.height + 1) issues.push(`세로넘침(가로AL) ${n.id} "${n.name}" +${Math.round(need - n.height)}`);
    }
    // ② 가로 넘침 — 부모 안쪽 폭보다 자식이 넓다
    if (AL(n)) {
      const inner = n.width - n.paddingLeft - n.paddingRight;
      for (const c of kids) if (c.width > inner + 1)
        issues.push(`가로넘침 ${c.id} "${c.name}" +${Math.round(c.width - inner)}`);
    }
    // ③ 무효 fill — 부모가 오토레이아웃이 아닌데 자식이 fill
    if (n.parent && !AL(n.parent)
        && (n.layoutSizingHorizontal === 'FILL' || n.layoutSizingVertical === 'FILL'))
      issues.push(`무효fill ${n.id} "${n.name}"`);
    // ④ 동명 형제 — 수정 잔재 의심
    const seen = new Set();
    for (const c of kids) {
      if (seen.has(c.name)) issues.push(`동명형제 "${c.name}" (부모 ${n.id})`);
      seen.add(c.name);
    }
  }
  return issues;
}
```

**①①-b②는 위반이면 무조건 결함**이다(§6 선언이 있으면 그 노드만 면제). **③④는 의심 신호**로, 발견 시 확인 후 판단한다 — ④는 반복 카드처럼 정당한 경우가 있다.

## 8. 빠른 체크리스트

1. 섹션은 세로 hug인가? 높이를 잠갔다면 연출 의도를 이름에 남겼나?
2. 영역·카드·행이 전부 "가로 fill · 세로 hug"인가? 아니라면 그럴 이유가 있나?
3. 행에서 **늘어나는 칸이 높이를 정하고**, 폭이 정해진 칸이 세로 fill로 따라가는가?
4. 배경 이미지를 흐름 밖(ABSOLUTE)으로 뺐나?
5. 여백이 패딩·간격으로만 만들어졌나? 빈 스페이서 노드는 없나?
6. 좌우 여백이 페이지 안에서 단일값인가?
7. 리스트 마커가 본문 첫 줄에 붙는가? (여러 줄이면 A 또는 B, B면 공식으로 재계산했나)
8. 글자의 늘어남 설정이 역할과 맞나? 본문에 "가로세로 자동"을 쓰지 않았나?
9. §7 판정식 4개를 돌려 ①②가 0건인가?
